Fresh and prepared are different experiments.

Prepared timings exclude setup and use graph replay. They cannot be subtracted from public timings to isolate overhead. The prepared campaign driver failed after writing data; serialized records were revalidated and summaries recovered. No campaign-gate success is claimed.

04 · Make the lifecycle explicit internally

Separate meaning, layout
and mutable execution state.

A simple public call can hide these boundaries. A public layout handle is optional until cross-program reuse justifies it.

01 / COMPILED PROGRAM

What to compute

Verified semantic MLIR, input/output facts, target identity and legal kernel families. No tensor addresses.

02 / OWNED LAYOUT

Which elements belong

A validated offset snapshot and bounds. Kernels read the exact snapshot checked; later source-offset mutation cannot alter it.

03 / BOUND EXECUTION

Where and when to run

Values/output storage, tasks, scratch and leases. One bound stream initially; separate state for concurrent runs.

Proposed convenience and reuse boundaries

program.run(values=values, offsets=offsets, out=output)

execution = program.prepare(values=values, offsets=offsets, out=output)
execution.run()  # Owns its validated layout snapshot.

Native function facts plus existing tensor validation and launch contracts can support the first slice. A universal typed ABI migration is not a prerequisite. Version counters alone cannot establish snapshot ownership.

Immediate errors still need a host decision.

For arbitrary fresh device offsets, moving validation onto the GPU does not eliminate synchronization while preserving an immediate exception before numerical execution. An asynchronous error token would be a different API.

Custom expressions need custom derivatives.

The derivative of sum(x*x) is not the derivative of sum(x). Initially reject gradient recording for arbitrary programs. Preserve the existing fixed operators' gradients; qualify graphs and training separately.

05 · A sequence with stopping rules

Earn each expansion.

The recommendation is an experiment with gates. You retain the decision about acceptable scope and performance cost.

  1. Repair contracts already shown to be wrong.

    Reject unsupported artifact subgroup widths. Correct unconditional numerical-error language and stale implementation-status text.

  2. Run caller-written programs through the current compiler.

    Add restricted source emission and native program facts. Reuse checked binding, direct execution and legal single-stage splits. Include owned preparation where reuse is useful.

  3. Test the abstraction with unfamiliar bodies.

    Freeze the subset, then add two held-out caller programs without changing production admission, dispatch or kernel-name tables. Compare equivalent fused Triton implementations.

  4. Let an application choose the next extension.

    Aligned inputs, fresh-layout dispatch, or split dependent stages. Each answers a different need; none requires a general task DAG or persistent queue.

Why not split dependent reductions immediately?

A straightforward split softmax has partial maxima, merged maxima, partial exponential sums using the full-segment maxima, merged sums and normalization. It needs explicit summary identity, ordering and storage. Chunk-local maxima cannot simply be combined by adding denominators. Five launches may lose to one direct kernel.

What did the independent reviewers disagree about?

The main objection to the recommended route is practical value: single-input inference may be too narrow. Weighted pooling first is stronger if a caller already needs two inputs. Fresh checked execution first is stronger if offsets rarely repeat. The reviewers also rejected mandatory public lifecycle ceremony and a universal ABI migration before the first useful program.

What remains unproven?

Performance of proposed APIs, arbitrary-program derivatives, application-level utility, multi-device portability, and custom composed-program GPU execution in the new feasibility check. Earlier broad tests passed for the existing implementation; they do not validate a proposed redesign. No sanitizer success is claimed.
